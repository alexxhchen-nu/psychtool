# psychtool 文稿与来源并排：设计简报

日期：2026-11-09。状态：用户已选择 A 方向；本文件整理设计意图，不代表新布局已经实现或视觉稿已验收。

## 使用任务与用户

模式：Operate。主要场景为 临床培训生整理多方材料，撰写一个报告章节，并对照来源进行人工复核。产品事实以根目录 `PRODUCT.md` 为准；界面为英文，与开发助手的讨论使用中文。

目标：用户在同一工作上下文中看清“正在写什么、依据哪段材料、哪些内容会发送给模型、哪些修改尚未保存”。现有端到端功能全部保留，不把安全步骤压缩成一个生成按钮。

## 已选结构

用户确认 A：文稿与来源并排。放弃分步骤向导作为主布局，因为反复修订需要持续对照，而不是频繁离开报告。

```text
顶栏：psychtool / Case / Report template / API status
┌──────────────┬──────────────────────────┬────────────────────────┐
│ Report       │ 当前章节与未保存状态     │ Sources / Model request│
│ sections     │                          │                        │
│              │ Section editor           │ 材料版本、来源原文     │
│              │                          │ 陈述归属、选入状态     │
│              │                          │ 或完整请求审批表面     │
│ Upload       │ Save / Review status     │ 当前阶段的明确操作     │
└──────────────┴──────────────────────────┴────────────────────────┘
```

- 左栏用于章节定位；上传入口固定可发现。已保存章节状态与编辑器的未保存状态分开表达。
- 中栏以正文为主；移除占据大量首屏空间的介绍内容，不新增营销指标。
- 右栏承担真实任务，而非静态状态图例。Sources 展示真实材料版本、来源段落、归属与候选陈述；Model request 展示冻结请求及独立审批/发送操作。
- 展开审阅时，右栏变宽，与正文并排；不是小尺寸弹窗，也不遮挡关键审批条件。
- 本轮仅设计桌面 Web，不制作手机交互稿或新增窄屏导航；保留已有响应式样式，不将手机适配列入本轮验收。
- 若某种来源定位尚无后端字段，只展示实际已有的 material/version/passage 信息，不伪造页码、坐标或证据关系。

## 视觉权威与表达

用户最新指定 CIJ（https://tcij.org/）为主要视觉参考，取代先前“必须保留 paper/forest、Manrope/Newsreader”的视觉约束。三栏任务结构、英文界面和桌面 Web 范围保持不变；正式页面目前仍是旧视觉，本轮仅调整设计方向。实际浏览器测量与候选 token 分层见 `references/design-extract/tcij-analysis.md`。

新方向以朱红、黑白、无衬线标题和平面分区建立信息层级；辨识点仍是“来源与文稿的对应关系”。借鉴 CIJ 的紧凑导航与编辑式主次关系，不复制巨幅活动图、轮播、捐赠模块或 90px 宣传标题。小字号白字操作拟使用经对比度检查的更深红色，而非直接照搬原站主红；具体字体、尺寸与 token 仍待可视化稿确认。

## 组件职责

- WorkspaceHeader：个案、模板、连接状态。
- SectionNavigation：章节定位和已保存状态。
- DocumentEditor：正文、未保存修改、保存与章节复核。
- SourceInspector：材料版本、原文段落、陈述归属和来源选择。
- RequestReview：完整预览、批准、单次发送及错误终态；复用已有 egress 状态机。
- StatusNotice：明确说明失败原因类别、当前状态和可执行恢复操作，不回显不安全服务端正文。

这些是职责边界，不要求为每个名称新增抽象层。继续使用 React 19、TypeScript、Vite 和现有 CSS；不因技能推荐而强制引入 Tailwind、shadcn 或新的状态管理依赖。

## 必须保留的状态与规则

- 请求 prepared/approved/sending/sent/invalidated/output_blocked/uncertain_failure 和章节 empty/draft/needs_review/approved 分开表达。
- Prepare、Approve、Send 是独立动作；完整预览、目的地、tier、source refs、指纹和确认条件必须可访问。
- 生成只填入未保存 draft，不能继承先前批准。请求恢复不承诺恢复生成正文。
- 来源变更使未发送请求失效；不确定投递与输出拦截禁止同请求重发。
- 长标题、长来源列表、完整 hash 和长 preview 必须换行或在明确区域滚动，避免页面横向溢出。
- 空材料、空章节、加载、上传失败、OCR 不可用、保存失败和断网均有明确反馈。
- 已保存数据之外的编辑状态在移动视图切换中保持；切换个案或章节的未保存处理需要在交互稿中验证。

## 交付边界与验收

本轮仅初始化产品上下文、记录工作流默认值与本简报，不改动 App、CSS、API 或数据库，不建立 DESIGN.md，不启动 Live 注入或修改 CSP。

下一步仅交付英文桌面 Web 可交互稿，使用显式标注的合成材料，展示来源对照和请求展开审阅。先确认该交互稿，再迁移正式界面。原有后端审批边界、测试覆盖与来源绑定必须保留；手机交互稿和移动端重设计暂缓。

待交互稿验证：常见桌面宽度下正文与审阅区的宽度分配；键盘导航和焦点回归；长请求预览；未保存状态；高密度来源列表。具体宽度和视觉微调由可视化验证决定，不当作用户已批准的数值。
